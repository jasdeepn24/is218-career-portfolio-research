Featured case study · IS218

One round.
A result you can check.

Rock Paper Scissors

View the RPS repository

Evidence reviewed November 23, 2026.
Source revision: f7dbcd0.

The problem

Complete the rules in a supplied course starter so a player can choose a move, see both choices and the correct result, then play another independent round.

My contribution & project context

The project work record documents my explanation of why Rock loses to Paper, review of a Scissors-versus-Paper win, and successful replay using Tab and Enter.

This is a course-starter project using an AI-guided development workflow. The repository contains the completed rule function and added tests; the interface and Flask server were supplied. The exact division of implementation work between me and AI assistance still needs my confirmation.

Technology & scope

Python keeps the winner rules in a small function, separate from the Flask request handler. pytest checks the rules and requests; Playwright exercises a browser round and replay. The scope stays deliberately small: one round at a time, without scoring or saved history.

Evidence & verification

  • Winner-rule implementation handles ties and the three winning pairs.
  • Rule and request tests cover all nine move combinations and a submitted Rock-versus-Paper loss.
  • Browser replay test checks a loss followed by a fresh winning round.
  • GitHub Actions run for the reviewed revision completed successfully on November 2, 2026.

These files and the recorded CI status were inspected for this portfolio. The RPS test suite was not rerun as part of the portfolio build.

Limitations & lessons to confirm

This demonstrates a bounded classroom workflow, not production delivery. There is no score persistence, and passing tests do not establish complete usability or performance.

The work record supports one concrete learning example: explaining how a test catches an incorrect result. My personal reflection on what was hardest, what changed my understanding, and what I would do differently is still to be confirmed.

Project case study · IS218

Highway Game: play, save, return.

Problem & implementation

Connect a Three.js highway game to a persistent account workflow: register, sign in, drive, save a result, sign out, and return to private scores. Flask serves the built game and authentication; SQLite stores accounts and results.

Implemented gameplay includes acceleration, braking, steering, traffic collisions, pause/resume, and a timed run. Results save after server confirmation, with a retry path for failed saves.

Contribution & evidence

This is my IS218 project. Merged integration PR #4 records 51 backend tests, 9 frontend tests, successful builds, browser checks, and owner verification of registration, login, gameplay, and saving. These are recorded project results; they were not rerun for this portfolio.

My individual implementation responsibilities and division of AI-assisted work still need confirmation.

Limitations & next steps

Controller support and full account maintenance are deferred. Score validation checks plausibility but is not cheat-proof. Run tickets expire after five minutes, and unsaved results remain only in the open tab.

Decisions & learning record

The integrated slice uses one origin for gameplay and accounts, and reuses run IDs when retrying saves to prevent duplicates. These are documented project decisions; my personal lessons still need confirmation.
